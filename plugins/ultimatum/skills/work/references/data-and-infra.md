# Data and infrastructure changes

Goal: change schemas, queries, access policies, and infrastructure-as-code safely: reversible, tested, and never applied to a real environment without the user's authorization. Loop basics: SKILL.md §3.

## 0. Hard rules

1. Never run migrations, DML, `terraform apply`, `destroy`, or `import` against staging/production unless the user explicitly authorizes that action on that target. Local/dev databases the project documents for testing are fine.
2. Connection strings, passwords, keys: never print or store them. Redact in notes and briefs.
3. Prefer the project's migration tool and layout (declarative vs imperative). Never invent migration file names; generate them with the tool (check `<tool> --help`) or follow the existing numbering.
4. Optional MCP/CLI integrations (Supabase, Postgres, Terraform/Registry MCP, cloud CLIs): use if present, name them first, run read-only operations by default. Without them, work from files and a local database.

## 1. Migrations

Checklist per migration:
1. **Reversible or explicitly one-way.** Write the down path (or document why none exists and what the backup/rollback plan is). One-way = say so in the report.
2. **Small and ordered.** One concern per migration. Never edit a migration that has been applied anywhere shared; add a new one.
3. **Zero-downtime order** (expand, migrate, contract), each as a separate deploy step:
   - Expand: add nullable column / new table / new index. No readers depend on it yet.
   - Deploy code that writes both and reads the old.
   - Backfill in batches; verify counts.
   - Deploy code that reads the new; later contract: add `NOT NULL`/constraints, drop the old.
   Never rename or drop a column in the same release that stops using it.
4. **Locks.** Know what the statement locks. Risky on large tables: `ALTER TABLE ... ADD COLUMN ... DEFAULT <volatile>`, adding `NOT NULL` or a FK validating the whole table, `CREATE INDEX` without `CONCURRENTLY`, type changes. Mitigate: `CREATE INDEX CONCURRENTLY` (outside a transaction), `ADD CONSTRAINT ... NOT VALID` then `VALIDATE CONSTRAINT`, set `lock_timeout`/`statement_timeout`, run off-peak.
5. **Backfills.** Batch by primary key range, idempotent, restartable, throttled, outside the DDL transaction. Log progress; count remaining rows. Include a dry-run count query.
6. **Test it:** apply to an empty local DB and to a DB seeded with representative rows; run down then up again; run the app's tests against the migrated schema. Quote exit codes (`ult run`).
7. **Data safety:** deleting or transforming data needs a backup/restore plan and the user's go-ahead.
8. Seeds and fixtures updated; generated types/ORM models regenerated by the project's command.

## 2. Query performance

1. Start with evidence: the slow query text, its frequency, and the plan. If you cannot see the plan, say so; do not guess indexes.
2. On a local or explicitly authorized database: `EXPLAIN (ANALYZE, BUFFERS) <query>` on realistic row counts. Note: ANALYZE executes the statement; wrap data-modifying statements in `BEGIN; ... ROLLBACK;` and never run on prod without authorization. Read: seq scans on large tables, row estimate vs actual, sorts spilling, nested loops over many rows.
3. Fixes in order: remove the N+1 (fetch with a join/`IN` batch/dataloader); select needed columns; add or fix an index; rewrite predicates so they are sargable (no function on the indexed column); paginate with keyset not large OFFSET; cache last.
4. **Index checks:** every foreign key column has a covering index (catalogue query: FKs whose columns are not the leading columns of any index); every column used in an RLS policy predicate, `WHERE`, `JOIN`, `ORDER BY` of a hot query; composite index order matches equality columns first, then range/sort.
5. N+1 detection: count queries per request in a test or log (`ult run` around a test with query logging); a count growing with row count is the bug.
6. Re-run the plan after the change: quote before/after execution times and plan shape. A change without a measured improvement is not a fix; use `optimization-loop.md` for iterative tuning.
7. Writes: short transactions, consistent lock ordering, `SKIP LOCKED` for queues, batch inserts, upsert for idempotency, pooled connections.

## 3. Supabase / Postgres row-level security: the 11 checks

Run for every table in a schema exposed to clients (`public` by default). Report each as pass / fail / not checked.
1. **RLS enabled** on every exposed table (`select relname from pg_class ... where relrowsecurity = false`). Grants are separate: also check which roles have table privileges.
2. **Policies target roles with `TO`**, not `auth.role()` checks (anonymous sign-ins carry the `authenticated` role).
3. **`TO authenticated` is not authorization.** The `USING` clause must carry an ownership or membership predicate, e.g. `(select auth.uid()) = user_id`.
4. **UPDATE has both `USING` and `WITH CHECK`**; INSERT has `WITH CHECK`. Otherwise a user can reassign rows to someone else.
5. **UPDATE needs a SELECT policy** too; without it updates silently match 0 rows. Tests must assert row counts, not "no error".
6. **No authorization from `user_metadata` / `raw_user_meta_data`** (user-editable). Use app metadata or a roles table. JWT claims can be stale until refresh.
7. **Views use `security_invoker = true`** (Postgres 15+), or live in an unexposed schema, or are revoked from `anon`/`authenticated`.
8. **`SECURITY DEFINER` functions**: set `search_path = ''`, check caller identity inside, `REVOKE EXECUTE ... FROM PUBLIC/anon`, put in an unexposed schema. Never add DEFINER just to silence a permission error.
9. **Storage**: upsert needs insert + select + update policies; bucket policies check ownership/path prefix.
10. **Service-role / secret keys** never in client bundles, `NEXT_PUBLIC_*`, or committed files (`ult scan`).
11. **Three-identity test.** Run as `anon`, user A, user B (and the service role as positive control). For each table and operation (select, insert, update, delete): own rows allowed; B reading, updating, or deleting A's rows returns zero rows or fails; anon gets nothing. Assert counts and the stored result, then confirm the negative test fails when the policy is removed (`security/secure-implementation.md`).

Performance of policies: wrap per-row functions as `(select auth.uid())` so they evaluate once; index columns used in policy predicates.
Changing policies is a security-relevant change: apply the overlay.

## 4. Terraform / infrastructure as code

1. Follow the repo layout (typically `versions`, `providers`, `variables`, `locals`, `main`, `outputs`). Variables are typed, described, and validated; pin provider and Terraform version constraints.
2. Checks, in order, each via `ult run`: `terraform fmt -check -recursive`, `terraform init -backend=false` (local validation without touching state), `terraform validate`, `terraform test` when tests exist (plan-mode `.tftest.hcl` run `command = plan`, with `mock_provider` for speed; apply-mode tests create real resources, so they need an authorized test account and an explicit timeout). Optional: `tflint`, `checkov`/`trivy config` if installed.
3. `terraform plan` needs credentials and reads state: run only if the user supplied/authorized access. Read the plan fully: count of create / update / destroy / replace. Any destroy or replace of stateful resources (databases, buckets, volumes, KMS keys, DNS) is a stop-and-ask.
4. **Never `apply` or `destroy`** without explicit authorization for that workspace; never `-auto-approve` on a plan you have not read. Never edit state by hand; `terraform state mv`/`import` only with approval, after a state backup.
5. **State safety:** remote state with locking; never commit state or `.tfvars` containing secrets; secrets via variables marked `sensitive`, environment, or a secret manager; check outputs that expose secrets.
6. **Module design:** group resources by lifecycle and coupling; module inputs typed with validation; outputs are the contract; keep cross-cutting concerns (tags, monitoring) outside. Refactors use `moved` blocks after reading real state addresses; done only when `plan` shows no create/destroy for moved resources.
7. Security defaults: no `0.0.0.0/0` on admin ports, encryption at rest on, public access blocked on storage, least-privilege IAM (no `*:*`). Apply the security overlay for IAM, networking, and CI permission changes.
8. For CI/CD-run Terraform, changing the pipeline is a deploy-setting change; see `release.md` §5.

## 5. Report

Per change: what is reversible, the exact commands run with exit codes, plan/EXPLAIN evidence, RLS checks (1-11) with pass/fail/not checked, anything applied to a real environment (should be nothing without authorization), rollback steps.

## 6. Quick commands (adapt to the project's tools; read-only unless stated)

- Tables without RLS: `select schemaname, tablename from pg_tables where schemaname = 'public' and not rowsecurity;`
- Policies listing: `select schemaname, tablename, policyname, cmd, roles, qual, with_check from pg_policies;`
- FKs without an index: join `pg_constraint` (contype 'f') against `pg_index` on the leading columns; report the table, column, and constraint name.
- Slow statements: `pg_stat_statements` ordered by `total_exec_time`; use it to choose what to tune.
- Supabase CLI: discover flags with `supabase --help` and `supabase db --help`; advisors and `db lint` if the installed version has them. Verify any fix by re-running the query as the test identity.
- Stop retrying the same failing command after 2-3 attempts; read the error and the docs for the installed version.

## 7. When to stop and ask

- A migration would lock a large table for an unknown time.
- A change drops, truncates, or rewrites data.
- A plan shows destroy or replace on a stateful resource.
- An RLS check fails and the fix would widen access.
- The only way to verify requires production credentials.
